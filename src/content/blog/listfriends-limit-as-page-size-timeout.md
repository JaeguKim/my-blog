## 증상

live에서 친구 목록 API `ListFriends`가 하루 15건 정도 3초 deadline을 넘겨 실패하고 있었다. 실패 로그는 전부 같은 모양이었다.

```
dynamodb Query ... canceled, context deadline exceeded
```

서버 지연은 3.00초 근처에서 딱 잘려 있었다. 요청 deadline 상한이다.

이 API는 이전에 한 번 손본 적이 있다. 친구 수만큼 presence를 Redis에 하나씩 묻던 N+1을 배치 1회로 바꿔 225ms를 13ms로 줄였다. 그런데도 꼬리가 남아 있었다.

## 먼저 어떤 요청이 느린지 본다

메시 지표(Istio)의 p99/p999는 쓰지 않았다. 같은 서비스에 WebSocket 업그레이드(`101`)가 섞여서 분위수가 오염된다. 대신 앱이 직접 남기는 Connect 접근 로그를 썼다. 요청마다 `rpcMethod`, `elapsed`, 요청 본문이 남는다.

- 1초 넘는 꼬리는 **`ListFriends`에만** 있었다. 같은 서비스의 `ListMyFriends`를 포함해 다른 친구 메서드는 최대 160ms 수준이었다.
- 완료된 `ListFriends`의 **98.5%가 `limit=1`**이었다.
- 1초 넘게 걸린 호출은 **100%** 같은 요청이었다.

```json
{"limit":1,"status":"FRIEND_STATUS_REQUEST_RECEIVED"}
```

앱 홈 화면이 "받은 친구요청이 하나라도 있나"를 확인해 배지를 띄우는 호출이다. 앱은 React Native라 Android와 iOS가 이 코드를 공유한다.

```ts
checkFriendRequestExists: async () => {
  const response = await deps.listFriends({
    accountId, cursor: '', limit: 1, status: FriendStatus.REQUEST_RECEIVED,
  });
  return response.friends.length > 0;
},
```

한 건만 달라는 요청이 가장 느렸다.

## limit은 행 수 상한이 아니라 페이지 크기였다

repo의 조회는 이렇게 생겼다.

```go
query := r.db.Query(keyCond).Limit(params.Limit)   // ← 클라가 보낸 limit
// ...status 필터
paginator, _ := query.Paginator(params.Cursor)

for paginator.HasNext() {          // 파티션 끝까지 드레인
    paginator.Next(ctx, &indexes)
    docs = append(docs, ...)
}
```

DynamoDB Query의 `Limit`은 "결과를 N개만"이 아니라 **"한 번에 N행씩 읽어라"**다. 그런데 이 함수는 파티션을 끝까지 드레인한다. 그러면 `limit`은 반환 개수를 줄이지 못하고 페이지만 잘게 쪼갠다.

> **Query 횟수 = 파티션 행 수 ÷ limit**

`limit=1`이면 행마다 Query를 한 번씩, **순차로** 보낸다.

함정이 하나 더 있다. status 조건은 FilterExpression이라 **읽은 뒤에** 적용된다. `Limit`은 필터 전 행 수에 걸린다. 그래서 받은 요청이 0건이어도 파티션의 모든 행(친구, 보낸 요청, 받은 요청)을 한 행씩 읽는다.

테스트 환경에 친구 290명인 계정을 만들어 재봤다.

| 요청 `limit` | Query 횟수 | Query span 합 |
|---|---|---|
| 1 | **×290** | **1,664ms** |
| 20 | ×15 | 90ms |
| 50 | ×6 | 37ms |
| 1000 | ×1 | (대조군) |

받은 요청이 0건인 상태로 잰 값이다. 그래도 290번 왕복한다. **적게 달라고 할수록 서버가 더 일한다.**

친구, 보낸 요청, 받은 요청에는 각각 300건 상한이 있다. 한 계정의 파티션은 수백 행까지 찬다. 거기에 네트워크 왕복 수백 번이 더해지면 3초가 금방이다.

## 왜 이렇게 됐나

이력을 따라가 보니 의도된 설계가 아니었다.

- 큰 아키텍처 리팩터 전의 repo는 `for paginator.HasNext() && len(res) < limit`로 **바운드돼 있었다.** 리팩터가 이 가드를 떨어뜨렸고, 요청의 `limit`은 그대로 Query에 꽂혔다.
- 석 달 뒤 누군가 목록에 중복이 생기는 걸 발견했다. 그런데 드레인을 고치는 대신 후처리 `DistinctBy`로 덮고 `// TODO: paginator의 근본 수정 필요`를 남겼다.
- proto는 `cursor`/`limit`/`next_cursor`로 진짜 커서 페이지네이션을 약속한다. 실제 서버는 전량을 돌려주고 `next_cursor`는 항상 비어 있다. 클라도 커서를 읽지 않는다.

지켜야 할 이유가 있는 담장인지 확인한 셈이다. 없었다.

그렇다고 바운드를 되살리는 게 답은 아니다. 앱은 온라인 친구를 앞에 보여주려고 **전체 목록을 받아 클라에서 정렬한다.** 50개에서 자르면 51번째 친구부터 사라진다. 전량 반환은 이미 앱이 기대는 계약이 됐다. 고칠 대상은 드레인이 아니라 **페이지 크기를 클라가 정하는 것**이다.

## 수정은 리뷰를 거치며 세 번 바뀌었다

**1차: 하한.** `max(limit, 1000)`. `limit=1`이 1000으로 올라가 한 페이지에 파티션이 다 들어온다. 클라 변경이 0줄이라 강제 업데이트가 안 되는 구버전 앱도 서버 배포만으로 고쳐진다. 이걸로 타임아웃은 사라진다.

하지만 클라 값이 여전히 페이지 크기를 정한다. `limit=1001`은 1001로 간다. 함정이 반만 닫혔다.

**2차: 고정 1000.** 클라 `limit`을 무시하고 1000으로 고정했다.

리뷰에서 바로 반론이 나왔다. 1000은 DynamoDB 기본 상한(1MB)보다 작은 인위적 상한이다. 친구 인덱스 행은 작아서 1MB면 수천 행이 들어간다. 1000을 넘는 파티션에만 이득 없는 왕복을 더할 뿐이다.

**3차: Limit을 아예 걸지 않는다.** 그리고 `limit` 필드를 repo 파라미터에서 지웠다.

```go
type queryParams struct {
    Cursor   string
    Status   enum.FriendStatus
    Backward bool
    // Limit 없음 — 클라 값이 DB 읽기 방식에 닿을 경로 자체를 없앤다
}

query := r.db.Query(keyCond)
if r.pageSize > 0 {          // 테스트만 설정한다. 프로덕션은 0 = 상한 없음
    query = query.Limit(r.pageSize)
}
```

필드를 남겨두고 "무시한다"는 주석을 다는 것보다 이쪽이 낫다. 주석은 다음 사람이 `params.Limit`을 다시 꽂는 걸 막지 못한다. 필드가 없으면 그러려면 일부러 코드를 바꿔야 한다.

이 변경으로 계약이 하나 바뀐다. `limit <= 0` 요청은 전에는 Query 쪽 검증에 걸려 `INTERNAL`로 실패했다. 이제는 전량을 돌려준다. 라이브 클라는 보내지 않는 값이다. 그리고 원래 `limit`과 무관하게 전량을 주는 API라 성공이 더 일관적이다. ADR에 새 계약으로 적었다.

### 테스트가 드레인을 실제로 지키는지 확인했다

여러 페이지를 끝까지 읽는지 검증하는 테스트를 넣었다. 그런데 기본 페이지에는 시드 몇 줄이 한 번에 다 들어온다. 그러면 드레인 루프에 바운드를 다시 넣어도 테스트가 통과한다. 첫 PR 리뷰에서 정확히 이 지적을 받았다.

그래서 repo에 테스트 전용 `pageSize`를 두고, 테스트에서 2로 내려 강제로 여러 페이지를 만들었다. 그리고 확인했다. 드레인 루프에 일부러 `break`를 넣으면 이 케이스가 깨진다. 깨지지 않는 테스트는 아무것도 지키지 않는다.

## 내가 틀렸던 것들

**"받은 요청이 많은 계정"이 아니었다.** 처음 정리한 문서에는 "친구가 많은 계정이 아니라 받은 요청이 많은 인기 계정이 느리다"고 적혀 있었다. 메커니즘을 다시 보면 틀렸다. 필터가 읽은 뒤에 걸리므로 왕복 횟수는 **파티션 전체 행 수**가 정한다. 290명 계정은 받은 요청 0건으로도 290번 왕복했다. prod에서 느렸던 게 인기 계정이었던 건 그런 계정이 대개 친구도 많아서일 것이다.

**"Android 문제"도 아니었다.** 느린 호출의 User-Agent가 대부분 `okhttp`라서 처음에 Android 홈 화면 문제로 적었다. 앱 코드를 열어보니 플랫폼 분기가 없는 공통 코드였다. `okhttp`가 많은 건 RN Android의 네트워크 스택이 okhttp이고 Android 사용자가 많아서다. 공지 문구까지 고쳤다.

**후속 티켓을 너무 일찍 만들었다.** 수정 후에도 배지 확인은 받은 요청 전량을 읽는다. 건마다 profile/presence/last-login을 붙여 다 내려준다. "개수만 세는 RPC를 만들자"는 티켓을 만들었다가, 근거를 다시 따져보고 내렸다.

- DB 왕복이 사라진 뒤 남는 비용은 최악 계정에서도 약 50ms로 추정된다.
- 수정 후 prod 수치가 아직 없다.
- IDL, 서버, 앱 배포가 다 필요하다. 그런데 정작 강제 업데이트가 안 되는 구버전 앱은 계속 옛 경로를 탄다.

선택지로 적어두고, 배포 후 데이터를 보고 정하기로 했다.

## 배포가 수정 직전 이미지를 올렸다

master 머지, release 브랜치 cherry-pick, live 재배포까지 끝났다. 속도를 재려고 로그를 열었는데 pod 이미지 태그가 이상했다.

```
container_image: 42.0.0-release-42.3af7137
```

`3af7137`은 cherry-pick 커밋의 **부모**다. 수정이 들어 있지 않다.

| 시각 (KST) | 이벤트 |
|---|---|
| 14:33:42 | release 브랜치에 cherry-pick push |
| 14:33:46 | 해당 커밋 CI(이미지 빌드) 시작 |
| **14:37:36** | **live 재배포 — 그 시점 최신 이미지 `3af7137`** |
| 14:39:24 | CI 완료 |

빌드가 끝나기 전에 배포를 눌러서 이전 이미지가 다시 올라갔다. 배포 완료 알림만 믿고 수치를 쟀다면 "개선 효과 없음"으로 결론 냈을 것이다. 수정 이미지(`dd7a0c1`)로 다시 배포했고, 14:43부터 교체돼 14:45에 롤아웃이 끝났다.

**배포 후 측정의 첫 단계는 수치가 아니라 이미지 태그 확인이다.** 같은 로그에 `container_image`가 찍혀 있으니 이미지별로 나누면 전후 구분도 시각 추정 없이 정확하다.

## 결과

live `ListFriends` 응답 로그를 **이미지 기준으로** 나눠 비교했다. 수정 후 구간은 배포 다음 날 아침까지 약 20시간이다.

| 구간 | n | p50 | p90 | p99 | p99.9 | max | 1초 이상 |
|---|---|---|---|---|---|---|---|
| 수정 전 (24시간) | 55,551 | 62.5ms | 863.7ms | 1,922.5ms | — | 3,001.2ms | 4,494 |
| 수정 전 (배포 직전 4.6시간) | 6,930 | 30.4ms | 579.4ms | 1,816.7ms | 2,639.1ms | 3,001.0ms | 366 |
| **수정 후 (약 20시간)** | **55,850** | **17.8ms** | **32.4ms** | **69.7ms** | **142.1ms** | **429.5ms** | **0** |

- p99가 1.8~1.9초에서 **70ms**가 됐다(약 27배). 1초 이상 호출은 0건이다. 500ms를 넘긴 호출도 없다. 가장 느린 호출도 정상 응답한 429ms다.
- 수정 전 24시간 실패 165건 중 29건이 3초 근처에서 끝났다. deadline에 걸린 호출이다. 수정 후 실패 31건은 모두 31ms 안에 끝났다. deadline 근처에서 끝난 실패는 0건이다.
- 배포 직후 19분(523건)만 봤을 때도 p99는 62ms였다. 약 20시간, 5.6만 건으로 늘려도 같은 수준이라, 친구가 많은 무거운 계정의 호출까지 섞인 결과로 볼 수 있다.

## 왜 아무도 몰랐나

마지막으로 이 타임아웃이 알림으로 잡혔는지 확인했다. 잡히지 않았다.

- 메서드 단위 latency/error 메트릭과 대시보드는 있다. 그런데 거기에 걸린 알림이 **없었다.**
- 가장 가까운 알림은 로드밸런서 전체의 p99 > 1초다. 하루 15건의 타임아웃은 전체 트래픽에서 티도 안 나서 이 알림은 7일 동안 0건이었다. 정상 동작이다. 그 알림이 보는 질문이 다를 뿐이다.

이번 건을 일찍 잡을 수 있었던 장치를 비용 순으로 적어둔다.

1. **메서드별 fault 건수 알림.** 메트릭이 이미 있어 바로 걸 수 있다. 비율이 아니라 건수 기준으로 건다. 하루 15건은 비율로는 소수점 아래다.
2. **요청당 DB 호출 수 메트릭.** 요청 context에 DynamoDB/Redis 호출 수를 세어 메서드별 히스토그램으로 남긴다. 이번 건은 "요청 1건에 Query 290회", 앞의 presence 건은 "Redis 290회"로 바로 보였을 것이다. N+1과 페이징 폭주를 한 번에 잡는 계측이다.
3. **느린 요청 구조화 로그.** 원인을 밝힌 건 결국 접근 로그의 `limit=1`이었다. 1초를 넘긴 요청만 메서드, 작은 요청 파라미터, User-Agent를 남기면 다음엔 쿼리 한 번이다.

---

남는 건 두 가지다.

**한 건만 달라는 요청이 가장 비쌀 수 있다.** "페이지 크기"와 "결과 상한"이 같은 이름(`Limit`)을 쓰고, 그 값을 클라가 정한다. 그러면 호출자가 적게 달라고 할수록 서버가 더 일하는 역설이 생긴다. 근본 해법은 DB 래퍼에서 `Limit`을 `PageSize`와 `MaxItems`로 나눠 이 함정을 표현할 수 없게 만드는 것이다. 같은 패턴이 다른 서비스에도 몇 군데 남아 있다.

**머지와 배포는 다르고, 배포 완료와 수정 반영도 다르다.** 이번엔 배포 완료 알림 뒤에 수정 직전 이미지가 떠 있었다. 측정 전에 이미지 태그부터 본 덕에 "효과 없음"이라는 잘못된 결론을 피했다.
